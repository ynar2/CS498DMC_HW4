Q1: FoundationDB separates its architecture into a Transaction Management System (TMS) and a Storage System (SS) to achieve independent scalability, fault tolerance, and clear separation of concerns. The TMS handles transaction coordination, sequencing, version assignment, and conflict detection, while the SS is strictly responsible for persisting key-value data and serving reads. This decoupling allows storage servers to scale horizontally without interfering with transaction coordination overhead.
Q2: The transaction's Proxy (specifically acting as the commit proxy in coordination with the Resolver) is responsible for detecting read-write conflicts between concurrent transactions. This check occurs during the commit phase right before a transaction is assigned a commit version, where the resolver checks if any keys read by the committing transaction have been modified by another transaction that committed after the read version.
Q3: The read version represents a consistent point-in-time snapshot of the database at which a transaction performs its reads, ensuring snapshot isolation. It relates to FDB's consistency guarantees by allowing transactions to read a stable, serialized version of data without locking, while the sequencer ensures that read versions are monotonically increasing and valid against committed transactions.
Q4: Standard reads check for read-write conflicts during the commit phase and will cause a transaction to abort if a conflict is detected, whereas snapshot reads ignore conflict detection and do not participate in conflict checking. You would choose a snapshot read when performing large, long-running read-only operations (like analytics or backups) where you want a consistent view without risking transaction conflicts or aborts.
Q5: FoundationDB's recovery is cheap because storage servers maintain durable state up to a specific version, and transaction logs (LogServers) stream mutations continuously so that recovery does not require replaying a traditional redo log from disk in the critical path. Instead, StorageServers coordinate with the new transaction proxy to quickly determine the recovery version, and any missing mutations are fetched directly from LogServers in parallel, avoiding heavy disk-based log playback bottlenecks.
